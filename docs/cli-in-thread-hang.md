# 第七个坑：长驻守护线程内调用 CLI，Bash 工具会挂住

记录日期：2026-10-26。适用于「文件到齐 → 调 CLI 自动执行」这类无人值守场景。

## 现象

守护进程（pythonw，无控制台）在**工作线程**里调用 `codebuddy -p ... --output-format stream-json`，请求「用 Bash 工具执行一条命令」。日志停在：

```
[会话] 启动｜model=...
[工具] Bash｜"C:/.../python.exe" -V
```

之后不再有任何输出：没有工具结果、没有 result 事件、没有报错。进程随后消失，调用方既拿不到返回值也拿不到异常。实测 4 次里 3 次复现。

## 对照实验（同一提示词、同一 model、同一端口）

| 调用方式 | 结果 |
| --- | --- |
| 终端前台直接调用 | 6~10 秒正常返回 |
| 最小环境变量 + `env -i` | 正常 |
| `pythonw` 启动脚本、进程内直调封装函数 | 正常 |
| **守护进程工作线程内调用** | **挂在 Bash 工具处** |

已排除的因素：`stdin=DEVNULL` 与 `CREATE_NO_WINDOW` 的四种组合全部正常；输出缓冲、端口占用（改为固定端口后仍复现）、鉴权（换成第三方 OpenAI 兼容端点后仍复现）。

## 结论

在这个进程形态下（无控制台父进程 + 工作线程 + 子进程内再起 bash），CLI 的工具调用链不可靠。**不要把它放在关键路径上**：宁可脚本通道失败就转人工，也不要让模型兜底卡住整条流水线。

## 处置建议

1. 可脚本化的部分一律写成确定性脚本，模型只做兜底，且兜底必须有硬超时。
2. 兜底调用要加「输出停滞」判定：连续 N 秒无新输出即杀进程并按失败处理，而不是等统一超时（本次统一超时是 3 小时）。
3. 若确实需要模型参与，改为独立进程 + 独立工作目录调用，不要把调用点放在长驻守护线程里。
4. 判定成功不要只看退出码：`subtype=error_during_execution` 时退出码仍可能是 0。

## 附：判断依据

同一封装函数在独立进程里调用正常（7 秒返回），在同一代码的守护进程线程里挂住；因此问题不在参数、不在模型、不在网络，而在进程与线程形态。此结论仅为实测现象，未定位到 CLI 内部具体原因。
